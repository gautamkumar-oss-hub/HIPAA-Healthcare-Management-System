# Healthcare Management System

A development MVP for a role-aware healthcare management system. It includes
authentication, patient profiles, appointment workflows, encrypted audit and
appointment events, simulated notification records, role-specific web
workspaces, and a token-forwarding assistant.

> **Development scaffold only.** This project has not undergone a formal HIPAA
> risk analysis, independent security assessment, or production-readiness
> review. It is not represented as HIPAA compliant and must not be used with
> real patient data. See the [risk assessment checklist](docs/risk-assessment-checklist.md)
> and the [implementation status](#known-limitations).

## Requirements

- Docker Engine with Docker Compose v2
- Git
- Available local ports: 5173 (frontend), 5432 (PostgreSQL), 6379 (Redis),
  8080 (gateway), and 9092 (Kafka)

The Java and frontend services are built in Docker. The AI service is configured
to use a local mock provider and does not call an external LLM.

## Run locally

1. Copy `.env.example` to `.env`. Set unique strong values for each database
   password and Redis password. Set `JWT_SECRET` to base64-encoded random data
   of at least 32 bytes and `FIELD_ENCRYPTION_KEY` to a separate base64-encoded
   random key of exactly 32 bytes. Set a strong bootstrap administrator
   password. Do not commit `.env` or use development credentials in production.
2. Build and start the services:

   ```sh
   docker compose up --build
   ```

3. Check service health and the frontend:

   ```sh
   curl http://localhost:8080/actuator/health
   curl http://localhost:8080/api/auth/actuator/health
   curl http://localhost:8080/api/patients/actuator/health
   curl http://localhost:8080/api/appointments/actuator/health
   curl http://localhost:8080/api/ai/health
   curl http://localhost:5173
   ```

4. Stop the services with `docker compose down`. To remove local database,
   Kafka, and Redis volumes as well, run `docker compose down -v`.

The bootstrap administrator must enroll TOTP before logging in. Public
registration creates patient accounts only; administrators can create staff
accounts. Patients can manage their own encrypted profile and appointments.
Doctors can manage their own availability and view assigned patient summaries.
Administrators can manage accounts and schedules and view audit records.
Appointment event handling currently records simulated email/SMS deliveries;
it does not send messages through an external provider.

To create synthetic local data, first sign in as the bootstrapped administrator
and enroll MFA. Then set `ADMIN_MFA_CODE`, `SEED_DOCTOR_EMAIL`,
`SEED_DOCTOR_PASSWORD`, `SEED_PATIENT_EMAIL`, and `SEED_PATIENT_PASSWORD` in
your shell and run:

```sh
python3 scripts/seed.py
```

The seed script uses the gateway and creates synthetic users and a sample
patient profile. Never use real patient information for local development.

## API documentation

The gateway API contract is in [docs/openapi.yaml](docs/openapi.yaml). It
documents current gateway paths, role requirements, and request/response
shapes. It is manually maintained and is not generated by the services;
update it when API behavior changes.

## Development

Run Java service tests with Java 21 and Maven:

```sh
mvn -B verify
```

Run frontend checks:

```sh
npm --prefix frontend ci
npm --prefix frontend run build
npm --prefix frontend test
npm --prefix frontend audit
```

Run assistant tests:

```sh
cd ai-agent-service
python -m pytest
```

## Known limitations

- The local Compose stack uses plaintext service and data-store connections.
- There is no completed organizational HIPAA risk analysis, formal security
  evaluation, incident-response program, workforce training evidence, BAA
  verification, or production operational approval.
- Secret management, certificate lifecycle, production TLS, backup/recovery
  procedures, production identity controls, retention policy, and
  privacy/operations review remain deployment requirements.
- Event publication and application database writes do not use a transactional
  outbox. Kafka consumers deduplicate events, but delivery and reconciliation
  are not guaranteed atomically.
- Notifications are simulated persistence only. The AI assistant uses a
  deterministic local mock and is not a clinical decision-support system.
- Automated unit and service tests do not replace PostgreSQL-backed end-to-end
  testing, independent penetration testing, load testing, or operational
  verification. Docker runtime validation may require access to a running
  Docker daemon.

Do not claim HIPAA compliance or use real PHI unless the deploying organization
has completed and approved the required legal, security, privacy, and
operational controls.
